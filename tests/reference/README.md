# Waterfall and claim reference calculations

Run from `/tmp/pra-lifecycle-integration` with Node 24 (tested on 24.10.0):

```sh
node --test --test-isolation=none tests/reference/calculator.test.mts
NO_DNA=1 cargo test --locked -p programmable-revenue-agreement --test reference_claim_vectors
rustfmt --edition 2021 --check programs/programmable-revenue-agreement/tests/reference_claim_vectors.rs
npm exec --offline --cache /tmp/pra-lifecycle-integration/target/prettier-cache --yes --package prettier@2.8.8 -- prettier --trailing-comma all --check 'tests/reference/*'
```

The Rust tests require the existing `target/deploy/programmable_revenue_agreement.so`
artifact and the repository's existing LiteSVM dependencies. After program changes,
build a fresh artifact before running runtime comparisons. This deliverable uses
the already built artifact and does not build or modify the program. The Node suite
uses native TypeScript stripping and Node's test runner, without adding dependencies
or changing the existing ES6 ts-mocha configuration. In-process test isolation avoids
the subprocess runner failure observed in this environment. Rust invokes Node to
read the same vectors through `export-claims.mts`; no second JSON parser dependency
or duplicate golden data is required.

## Reuse and arithmetic

Import `waterfall`, `allocateSplits`, `accrue`, and `claim` from `calculator.mts`.
Pass base-unit quantities as `bigint`. `vectors.json` stores those quantities as
**decimal strings**, including values above JavaScript's safe-integer limit.
`vectors.mts` provides a reusable decoder. Tier counts and sequence indices are
JSON numbers; flags are booleans. Expected results are explicit values derived
from the formulas below, rather than generated by the calculator under test.

- For cumulative total `D`, tier filling is
  `min(D, upper) - min(D, previousUpper)`, with first lower bound zero.
  A deposit allocates the difference between filling after and before the deposit.
  Strictly increasing thresholds finish at `u64::MAX`; total deposits remain `u64`.
  This interval formula is independent of an iterative tier-filling implementation.
- Each basis-point split is `floor(amount * bps / 10000)`. The remainder of the
  deposit is reported as `unallocated`; scaled per-split residues are also returned.
- Accumulator increment is `floor(holderRevenue * 1e12 / entitlementUnits)`.
  `scaledRemainder` reports numerator modulus denominator, without inventing carry.
  `integerDust` is the allocation minus the aggregate hypothetical claim of all
  entitlement units for this increment. Separate holders can leave additional dust.
- For each active tier, earnings are
  `floor(balance * (acc - last) / 1e12)`. Add existing pending amounts, then sum
  payouts with checked `u64` arithmetic. Multiplication and accumulator arithmetic
  are bounded by `u128`. A positive, funded claim snapshots active accumulators and
  clears their pending amounts; inactive slots stay unchanged. Frozen, zero-payout,
  insufficient-vault, and overflow cases reject without mutating inputs.
- Sequences explicitly model allocations that are **100% for holders**, a constant
  holder balance and denominator, and no fractional accumulator carry. They check
  successive deposits, claims and vault conservation, rather than claim to implement
  the missing deposit or transfer-hook instructions.

There are 79 golden cases: 16 waterfall, 8 split, 8 accrual, 13 claim, 7 sequence,
and 27 invalid-input cases. Conservation and input immutability are checked alongside
exact outputs. The three Rust tests cover 22 runtime claim vectors (normalizing the
reference diagnostic `NarrowingOverflow` to on-chain `MathOverflow`), a focused overflow
rollback regression, and the still-unresolved claim-timing discrepancy.
Injected fixtures exercise accounting and transfer CPI, not initialization or
reachability of every extreme accumulator state. Payment and entitlement fixtures
use basic Token-2022 accounts; extension-specific deposit/transfer behavior is outside
this arithmetic test suite.

## Specification boundaries and discrepancies

The repository has no `deposit_revenue` implementation. Therefore these helpers do
not decide whether cap-crossing deposits are accepted, rejected, or clipped; `endCap`
only reports the expiry signal and excess. Nor do they decide whether the accumulator
denominator should be contractual supply, sold supply, or another value. Callers
must supply it explicitly. Independent split floors and residual reporting are
arithmetic diagnostics, not a decision about residual routing or remainder carry.
These choices need confirmation before matching a future deposit implementation.
The available state, initializer, claim handler and README are the basis for this
suite; no separately supplied protocol-study-guide file was found in this checkout.

The SBF runtime tests track the following accounting findings:

1. **Unsafe narrowing — fixed.** For balance `1`, delta accumulator
   `18446744073709551616000000000000` and pending `1`, mathematical earnings are
   `18446744073709551616` (`u64::MAX + 1`). Previously the unchecked cast paid only
   pending and advanced the snapshot. The program now uses checked `u64::try_from`
   and returns the existing `MathOverflow` error. The reference keeps its precise
   `NarrowingOverflow` diagnostic, mapped to the program error by the runtime harness.
   `earnings_narrowing_overflow_rejects_without_state_changes` checks the exact error,
   absence of token CPIs, and unchanged config, all five tiers, ClaimRecord, both
   mints and token accounts. The original vector's discrepancy metadata is historical;
   it no longer describes current program behavior. Boundary and successful claim
   vectors remain covered, including the maximum valid `u64` payout.
2. **Claim timing changes payout.** For two entitlement units, a holder balance of
   one and two holder allocations of three, accumulator snapshots are `1.5e12` and
   `3e12`. Claiming at each snapshot pays `1 + 1 = 2`; waiting pays `3`. Successful
   claims discard fractional residues. Both sequence vectors and
   `documented_claim_timing_rounding_discrepancy_is_reproduced` show this behavior.
   The repository README's claim-timing independence statement needs reconciliation
   with integer rounding and the lack of fractional carry.

Passing discrepancy tests means the documented behavior was reproduced, not that
it agrees with the intended economic design. Strict reference overflow checks are
not weakened to mimic truncation. Fractional-residue accounting remains unchanged
and requires a separate protocol decision and implementation review.
