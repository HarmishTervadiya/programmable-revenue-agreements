## Unresolved issues and decisions

1. **Unchecked narrowing — corrected code defect (R11/R13).** With balance `1`,
   accumulator delta `18446744073709551616000000000000`, pending `1` and vault `1`,
   mathematical earnings are `u64::MAX + 1`. The historical cast paid pending alone
   and discarded earnings. Checked conversion now rejects with `MathOverflow`;
   the reference names this diagnostic `NarrowingOverflow`. The SBF regression
   verifies no token CPI and unchanged accounts, snapshots, pending and balances.
   Maximum representable payout remains covered. Historical vector metadata is
   retained as regression context, not a description of current behavior.
2. **Discarded claim fractions — documented economic mismatch and specification
   decision (R12/R14).** Two units outstanding, holder balance one, and two holder
   allocations of three yield snapshots `1.5e12` and `3e12`. Frequent claims pay
   `1 + 1 = 2`; delayed claim pays `3`. The README promises timing independence;
   decide whether to preserve fractions or revise that promise. No rule is invented.
3. **Missing deposits — implementation gap (R06/R07).** Neither vault-funding
   authorization nor on-chain waterfall/accumulator updates exists. Injected-state
   runtime tests and simulated sequences do not substitute for this instruction.
4. **Denominator, cap crossing, residual routing — specification decisions
   (R08/R09/R10).** Confirm supply versus sold units (including treasury treatment),
   reject/accept/clip policy, and ownership/carry of split and accumulator residues.
   Reference outputs report these quantities without selecting an economic policy.
5. **Post-closure account lifetime — specification decision plus missing supporting
   implementations (R27/R30/R32/R33).** Closure intentionally retains the mint and
   ClaimRecords while deleting config, tiers and ExtraAccountMetaList. The retained
   mint's freeze authority is still the config PDA and the transfer hook is locked
   to this program with no update authority. Default token accounts are Frozen.
   Current freeze/unfreeze require a deserializable config, so those entrypoints
   cannot thaw retained accounts after closure. A PDA does not cryptographically
   cease to exist when its account closes, but no recovery signing path exists here.
   Current claims also require deleted accounts, and no transfer callback or
   independent ClaimRecord-close instruction exists. Post-close transfer, burn,
   thaw and rent recovery must be explicitly decided and tested; retention alone
   establishes none of these capabilities. Do not treat closure as checking every
   holder's pending amount: the decided gate uses vault dust/deadline, with no registry
   or outstanding-claims counter.
